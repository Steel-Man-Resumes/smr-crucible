## 0. Verdict, plainly

The platform is real, live, and substantially good. The intelligence layer Opus built -- the bullet workshop, the readiness-aware analysis, the journey engine, decision logging, partner infrastructure -- is genuinely differentiated and mostly honors the doctrine. Troy's own run produced a strong Career Intelligence headline/summary and a usable base resume on the first end-to-end pass. That is not nothing; most products never get there.

**But the platform's central promise -- truth-preserving extraction -- is enforced in only ONE of its four resume-writing lanes.** The bullet workshop holds the iron gate. The Forge document generator, the Application Tailor, and (by inheritance) the rush lane all carry explicit instructions to *invent plausible numbers*. The artifacts from Troy's own test prove it shipped fabricated metrics to an employer-facing document. For this population -- people whose claims get extra scrutiny and who must survive background-checked interviews -- a fabricated "less than 1% rework rate" is not a quality nit. It is the exact liability the product exists to eliminate, generated by the product.

Everything else below is fixable polish by comparison. Fix the truth gate first.

## 1. P0 -- must fix before the EXPO cohort touches it (target: this week)

### P0-1. The truth gate is absent from both document-generation lanes (CONFIRMED, artifact-proven)

- `apps/consumer/app/api/resume-generate-full/route.ts:136` -- "Numbers in EVERY bullet. **Estimate conservatively from industry context if source has no numbers.**" and `:141` -- "But DO quantify achievements from context."
- `apps/consumer/app/api/forge/generate-docs/route.ts:150` -- "Numbers in EVERY bullet... If the source data has no numbers, **ESTIMATE CONSERVATIVELY from industry context**" (and `:294` simultaneously says "Never fabricate achievements" for the cover letter -- the file contradicts itself).
- Contrast the one lane that does it right: `app/api/forge/resume-assist/route.ts:31-45` (`BULLET_SYSTEM`) -- "Use ONLY the facts the person gave you. Never invent a number, a tool, a result... A strong TRUE bullet beats an impressive false one. Their story has to survive an interview."

**Artifact evidence from Troy's run** (tailored resume for Forklift Operator @ Snelling): "less than 1% rework rate across production runs," "department-wide cleanliness rating that passed all facility audits," "Identified and reported 3+ recurring assembly defects," "ISO-aligned quality certifications," "zero product damage recorded" -- none of these exist in the base resume. The cover letters add "I have reliable transportation" and "I'm built for physical work" (echoing the JD's requirements as personal claims).

This violates locked spec 11.2 ("no generated bullet ships without traceable evidence... never invents") and the charter doctrine ("a violation IS a bug"). It also poisons downstream tools: Interview Practice now probes bullets the user can't back, and the readiness checklist asks "can you explain every bullet out loud?" about bullets the machine invented.

**Fix:** Port the workshop's iron rules into both prompts. Where a bullet lacks numbers: keep it un-quantified, or route through progressive intake to ASK (the engine for this already exists: `lib/intake-engine.ts`). Replace "Numbers in EVERY bullet" with "Numbers where the source provides them; never estimate." Add a post-generation check pass if needed (compare generated quantities against source text; strip unsourced ones). Half a day of prompt surgery + verification.

### P0-2. Shared-IP rate limits will 429 the cohort mid-Forge (CONFIRMED)

- `packages/core/src/rateLimit.ts:11-24`: `analyze: 5`, `parse: 10`, `assistant: 20`, `rush-resume: 5`, `generate-docs: 5` per **IP** per day.
- `lib/withRateLimit.ts:113` (mode "ip") never checks auth -- signed-in users on Forge endpoints still share the IP bucket.
- A classroom / program lab / library is one NAT IP. Person #6 in Marianne's cohort gets "you've used all your free AI calls" on `/api/analyze` mid-flow. Same failure mode threatens the Aug 14 live room.

**Fix options (pick one this week):** (a) partner-code-aware pre-auth limits -- the Forge session already enters via `/access?code=EXPO2026`; carry the code in forge-session requests, validate server-side against `access_code`, and count against a generous per-code bucket instead of the IP; (b) auth-aware IP exemption (if a valid session cookie exists, use per-user limits even on forge endpoints); (c) blunt: temporarily raise analyze/generate-docs/parse 10x for cohort week. (a) is the durable one and also gives you per-partner usage telemetry for the pilot data story.

### P0-3. Partner-code tier tension (KNOWN, still unresolved -- now pilot-blocking)

`HANDOFF.md` already flags it: redeeming a partner code elevates the redeemer to tier `partner`, which skips the client journey/onboarding. If Marianne's cohort members redeem EXPO2026 themselves, they don't experience the product you want piloted (and the pilot data is garbage). Either split role from rate-limit tier before June 16, or instruct Marianne's team explicitly: cohort members sign up WITHOUT the code (the code is for staff), and solve their rate limits via P0-2.

## 2. P1 -- the employer-facing artifact layer (the product IS the resume)

### P1-1. Identity desync: one user, two names, mixed documents (CONFIRMED, DB-proven)

- Base resume artifact `contact.name` = "Troy Richard Carr" (typed in the Forge builder). `users.name` = "Marcus Relly" (typed at signup). Tailored resume + its cover letter = "Marcus Relly" with raw phone `2623918137`; base resume + generic cover letter = "Troy Richard Carr" with formatted phone.
- Mechanism: `ResumeWorkspace.runCareerPackage` (`components/resume/ResumeWorkspace.tsx:264-269`) sources contact ONLY from `/api/user/profile`; the profile route (`app/api/user/profile/route.ts`) takes name from the auth session first, then backfills phone from the most recent resume artifact. The base resume's contact block is never the source of truth, and nothing warns about the mismatch.
- Aggravator -- contact clobber (CONFIRMED): `packages/core/src/forgeSession.ts` upserts `profile_data = EXCLUDED.profile_data` (full replace). Register writes `contact` after forge-persist, but any later forge re-sync (`/api/forge/save` relay, `app/(dashboard)/layout.tsx:214-228`) replaces `profile_data` and wipes `.contact`. Empirically: the dev tester's `consumer_profile.profile_data.contact` is NULL despite registering with a name.

**Fix:** (1) make the `saveForgeSession` upsert merge-preserve `contact` (jsonb merge, not replace); (2) Tailor takes contact from the base resume doc, profile as fallback, with a one-line editable confirm ("This resume is for: Marcus Relly, 262-391-8137 -- edit"); (3) normalize phone formatting at one choke point.

### P1-2. Certifications cannot survive the structured pipeline (CONFIRMED)

`ResumeDocument` (`components/resume/resumeModel.ts:8-27`) has no certifications field; the Tailor's generation schema (`resume-generate-full/route.ts:104-130`) has none either. Troy's forklift certification existed only in the AI resume *text* (the Career Analysis lane) -- so the tailored resume for a FORKLIFT job dropped the forklift certification, while its cover letter mentions it. For this population (forklift, OSHA, CDL, ServSafe, trade certs), certifications are frequently the single most valuable line on the page.

**Fix:** add `certifications[]` to the model + a section editor + `parseResumeText` mapping + the Tailor JSON schema + both formatters. Also: tailored output dropped Education entirely in Troy's run -- enforce "carry base sections forward unless the user removes them."

### P1-3. The Tailor never uses the structured base resume (CONFIRMED)

- `runCareerPackage` feeds the AI only `forge_session` text + forgeOutput (localStorage, falling back to `/api/forge/load`); `parseForgeToResume` (`components/resume/resumeParsers.ts`) re-derives from text and ignores `session.resumeDoc`. The persisted base artifact -- with the user's edits and bullet-workshop evidence -- is never loaded. Spec section 4's "the base resume becomes the default the Tailor pulls from" is unwired in the generation path.
- Cross-device break (CONFIRMED by reading): `forgeAvailable` and `importFromForge` are localStorage-only (`ResumeWorkspace.tsx:119-129, 538-548`). On a new or shared device the Tailor tells a user with a saved base resume to "Build your base resume in the Forge first." This population uses shared computers; continuity is not optional.

**Fix:** Tailor default-loads the newest `source:"forge"` artifact server-side (it's already in `/api/user/context.resumes[]`), feeds the structured doc (with evidence) to generation, and offers "use my base resume" as the primary path regardless of device.

### P1-4. The export pipeline undermines the work (CONFIRMED, multiple)

1. **Two divergent HTML print templates:** `components/resume/resumePrint.ts` (navy banner + footer) vs `app/(forge)/output/page.tsx:933` (clean header, separate CERTIFICATIONS, no footer). Same product, two different resumes.
2. **Duplicate-name bug:** `buildResumePrintHtml` prepends a name banner but prints `formatResumeDownload` text that begins with the name; the all-caps heuristic (`resumePrint.ts:29`) renders the in-body name as a section header. Troy's tailored PDF shows "MARCUS RELLY" twice.
3. **Browser print chrome on real documents:** both PDFs carry "6/9/26, 7:21 PM ... about:blank ... 1/2" headers/footers. A jobseeker will not know to disable those. These are application documents going to employers.
4. **The Career Analysis PDF is a 2.2MB textless artifact** (text rendered as vector outlines -- not selectable, not screen-readable, not parseable). Likely the print pipeline + font path; needs a look at how Chrome is embedding the output-page fonts.

**Fix direction:** one template; set a real `document.title`; either move to server-side PDF generation (one clean dependency, e.g. running the existing print HTML through headless Chromium in a route) or, minimum, instruct in the print dialog UI ("turn OFF headers and footers") and strip the in-body contact block when the banner renders. Mobile note: `window.print()` on Android is rough -- server-side PDF + direct download is the population-correct answer.

### P1-5. "Built with The Refinery - steelmanresumes.com" on employer-facing resumes is an indirect disclosure (CONFIRMED)

`resumeModel.ts:264` appends it to every text/PDF export (also `ResumePreview.tsx:198`). steelmanresumes.com publicly brands as a justice-impacted service; an employer who Googles the footer learns what the candidate did not choose to disclose. Doctrine: disclosure is its own lane, never on the resume. It also contradicts the master-plan brand rule (Forge/Refinery names are internal-facing only).

**Fix:** remove from exported artifacts (keep in-app), or make it an explicit opt-in checkbox at export. 30 minutes.

### P1-6. "Coaching, not legal advice" is missing everywhere it's required (CONFIRMED)

Master plan §16: non-negotiable, "Every output must include this framing." Today: the disclosure plan UI renders "Know your rights" with statute citations, the plan PDF (`disclosure/page.tsx:294-324`) has a "Your Legal Rights" section, the vault PDF (`vault/page.tsx:140-148`) has "Your Rights" -- zero disclaimers on any of them. Worse, for non-WI users `disclosure-guide/route.ts:97` instructs the model to "Research the specific ban-the-box laws... cite the actual statute" -- the model cannot research; it recalls or confabulates statutes, presented authoritatively. Practitioners at Reentry United will look for exactly this line and its absence.

**Fix:** disclaimer component on the plan view + a line in every disclosure-touching PDF; for non-WI jurisdictions, soften to "general guidance -- verify with a reentry legal resource" and stop demanding statute citations the model can't source. (WI's curated block is fine.) 1-2 hours.
